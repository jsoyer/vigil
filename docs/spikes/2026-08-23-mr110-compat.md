## Verdict : **FULL** sur les deux sites

Bibliothèque validée sur matériel réel : **`tplinkrouterc6u==5.31.1`**
(à épingler strictement dans `requirements.txt`, Sprint 2).

| Site | Hôte d'exécution | MR110 | Auth | Verdict |
|---|---|---|---|---|
| Dijon | bbh-dij-guardian (DietPi) | 192.168.10.1 | OK | FULL |
| Nice | bbh-nce-guardian (DietPi) | 192.168.30.1 | OK | FULL |

Rapports bruts : `/home/dietpi/spike-mr110-{dijon,nice}.json` sur chaque

## Topologie réelle constatée (remplace l'hypothèse « Pi Zero dédié »)

Il n'y a **pas** de Pi Zero pont séparé : les **guardians eux-mêmes** portent
le lien vers le MR110 de leur site (sous-réseaux dédiés `192.168.10.0/24`
Dijon, `192.168.30.0/24` Nice). Conséquences :

- Depuis les **guardians** (instances slave) : MR110 joignable en direct →
  mode **`bridged`** au sens C16 pour ces instances.
- Depuis les **masters** (bbh-network, penelope) : MR110 **non routable**
  (vérifié : ping 192.168.10.1 KO depuis bbh-network) → mode **`remote`**
  pour ces instances (exécution via le guardian, SSH ponctuel — C11).
- Le « pont » étant un hôte watchdog à part entière, la contrainte C7
  (« pont non applicatif ») est **sans objet dans cette topologie** : la lib
  vendor peut vivre dans le venv Vigil des guardians. Consigné comme
  amendement de contexte, pas comme violation.

| Commande | Disponible |

| `reboot` | ✅ |
| `get_sms` / `send_sms` / `set_sms_read` / `delete_sms` | ✅ |
| `send_ussd` | ✅ |

Métriques exposées et lues avec succès : `network_type=3` (4G),
`sim_status=3` (SIM OK), `isp_name=Free`, `sig_level`, `rsrp`, `rsrq`, `snr`,
compteurs de trafic, vitesse courante, compteur SMS non lus.

## Mesures de signal au moment du spike (calibrage readiness, Sprint 2)

| Site | RSRP | RSRQ | SNR | Barres |
|---|---|---|---|---|
| Dijon | −99 dBm | −14 dB | −20 | 3/5 |
| Nice | −103 dBm | −18 dB | −70 | 3/5 |

Note : le SNR remonté (−20 / −70) semble être dans une unité/échelle propre
au firmware (des SNR en dB seraient aberrants à ces niveaux avec un service
fonctionnel). **À traiter au Sprint 2** : ne pas utiliser le SNR brut dans la
readiness sans clarification, ou le seuiller très bas par défaut. Les seuils
par défaut de la spec (`RSRP_MIN=-110`) sont cohérents avec les valeurs
observées.

## Points ouverts pour le Sprint 2

1. `wan_ip` non remonté dans le rapport du spike — vérifier le champ exact de
   la lib (5.31.1) ; la preuve de chemin C11 (IP publique différente du WAN
   principal) reste à implémenter dans la sonde du driver.
2. 4 SMS non lus sur le MR110 de Dijon (probablement opérateur) — bon cas de
   test réel pour `get_sms` quand les commandes SMS arriveront.
3. Aucun reboot déclenché pendant le spike (`reboot_called: false`) —
   l'inventaire des commandes s'est fait par introspection, pas par exécution.
